## 2. Critical Verification A: Deadline Alert Background Scheduler

### Prior Gap Identified
Previously, deadline reminders were generated by an on-demand service method triggered solely through an administrative endpoint (`POST /api/v1/notifications/trigger-check`). The platform lacked an autonomous background worker to scan approaching deadlines and deliver reminders without manual intervention.

### Implementation Details
- **Scheduler Service**: Authored `DeadlineAlertScheduler` in `backend/app/services/deadline_scheduler.py`.
- **Async Background Task**: Uses an `asyncio.Task` that sleeps for a configurable interval (`DEADLINE_ALERT_INTERVAL_SECONDS`, default 300s).
- **Session Isolation**: Allocates a fresh `AsyncSessionLocal` instance per tick to prevent cross-request session contamination and connection leakage.
- **Concurrency Guard**: Incorporates an `asyncio.Lock` preventing overlapping execution if an evaluation tick runs long.
- **Graceful Lifecycle Management**: Tied directly to FastAPI's `lifespan` context in `backend/app/main.py`. The scheduler starts on application boot and cancels gracefully on shutdown.
- **Configuration**: Added `DEADLINE_ALERT_ENABLED: bool = True` and `DEADLINE_ALERT_INTERVAL_SECONDS: int = 300` in `backend/app/core/config.py`.

### Evidence of Verification
Authored dedicated test suite `backend/tests/test_deadline_scheduler.py` verifying:
1. Deadlines > 48 hours away do not generate premature notifications.
2. Deadlines <= 48 hours generate a `DEADLINE_48H` notification and persist to PostgreSQL.
3. Passed deadlines generate a `DEADLINE_OVERDUE` alert.
4. Subsequent scheduler ticks are idempotent and do not create duplicate alerts.
5. Overlap locking prevents concurrent executions from running simultaneously.
6. Multi-company tracking generates alerts independently for distinct companies.

All 88 backend tests passed cleanly in 28.90s.

## 4. Critical Verification C: Security & Secrets Audit

### 4.1 Authentication & Credential Storage
- **Password Hashing**: Implemented with Argon2id (`argon2-cffi`) using parameters `time_cost=3`, `memory_cost=65536` (64 MB), `parallelism=4`, and cryptographically random 16-byte salt in `backend/app/core/security.py`.
- **JWT Signature & Expiry**: Tokens are signed using HS256 with a 256-bit secret key, enforced with an expiration window of 120 minutes. Token claims include `sub` (User ID UUID) and `role` (`ADMIN` or `MSME_USER`).
- **Token Storage**: In the frontend (`frontend/src/api/client.ts`), access tokens are stored strictly in `sessionStorage` (`tender_bid_token`). Tokens do not persist across browser sessions or tab closures, neutralizing permanent cross-session credential persistence vulnerabilities. Tokens are transmitted exclusively via the standard `Authorization: Bearer <token>` HTTP header.

### 4.2 Multi-Tenant Isolation
- **Document Isolation**: Queries in `backend/app/api/routes/documents.py` and `DocumentRepository` enforce `company_id == current_user.company_id`. Cross-company document downloads return `HTTP 404/403`.
- **Compliance Reports**: Reports are owned by `company_id`. The list and retrieval endpoints verify ownership and return `HTTP 404` when an authenticated MSME attempts to read another company's evaluation.
- **Bid Applications & Notifications**: Filtered by `current_user.id` and resolved `company_id`. Tenant boundaries verified in `tests/test_bid_tracking.py` and `tests/test_documents.py`.

### 4.3 Sandboxed File Upload Security
- **Magic Bytes Validation**: Files must start with `%PDF-` magic bytes. Uploads with disguised extensions (e.g. `.exe` renamed to `.pdf`) are rejected with `HTTP 400 Bad Request`.
- **Size Bounds**: Maximum payload capped at 25 MB. Oversized files are rejected before processing.
- **Path Traversal Protection**: Filenames are sanitized via `os.path.basename` and stored using deterministic UUIDs in isolated storage paths. Attempts containing `../` or `..\` are trapped and rejected.
- **Integrity**: Every document is hashed with SHA-256 upon arrival and verified prior to text extraction.

### 4.4 Defense-in-Depth Middleware
- `SecurityHeadersMiddleware`: Injects `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `X-XSS-Protection: 1; mode=block`, and `Referrer-Policy: strict-origin-when-cross-origin` on all HTTP responses.
- `InMemoryRateLimiter`: Enforces sliding-window rate limiting on `/api/v1/auth/login` (5 requests/minute) and `/api/v1/compliance/analyze` (10 requests/minute).

### 4.5 Dependency Vulnerability Audit (`npm audit`)
- Running `npm audit` in `frontend` reports 12 transitive vulnerabilities in development dependencies:
  - `tinypool` (prototype pollution in Vitest worker pool)
  - `braces` (deeply nested pattern CPU consumption via Tailwind CSS build toolchain)
  - `postcss-selector-parser` (flat selector CPU exhaustion)
  - `react-router` (open redirect handling via backslash)
- **Impact**: All flagged vulnerabilities are restricted to build-time devDependencies (`vitest`, `tailwindcss`) or internal routing helpers. None are exposed to untrusted external input in the compiled production bundle (`dist/`). Resolving them requires major breaking version migrations (`tailwindcss` v4, `vitest` v5, `react-router` v7).

### 4.6 External Gemini API Keys & Fallback
- `backend/.env` was inspected securely: billable Google Gemini API keys are not present in the local environment.
- **Architectural Fallback**: `GeminiClient` in `backend/app/services/ai/gemini_client.py` implements a graceful `_deterministic_fallback`. When `GEMINI_API_KEY` is not present, the service produces factual, deterministic summaries without failing the evaluation or calling external endpoints. Deterministic compliance scoring is 100% independent of external AI availability.

## 5. Critical Verification D & E: Deterministic Rules & AI Separation

### Deterministic Supremacy Invariant
The platform enforces a strict separation of concerns between objective Python arithmetic and AI-generated narrative summaries:

```
[Procurement Rules & Company Proofs]
                 │
                 ▼
   [Deterministic Rule Engine]  <--- PURE PYTHON ARITHMETIC
                 │
                 ├── PASS / FAIL / MISSING_EVIDENCE
                 │
                 ▼
     [Reconciliation Guard]    <--- HARD ENFORCEMENT GATE
                 │
                 ├── If any mandatory rule FAILS ──> Overall Status: NOT_ELIGIBLE
                 │                                  Score capped; AI override blocked
                 │
                 ▼
       [LangGraph Orchestrator]
                 │
                 ├── Hybrid RAG (PostgreSQL Lexical + ChromaDB Semantic)
                 ├── Citation Validator (Validates page numbers & file bounds)
                 └── Gemini Explanation (Explains objective result; CANNOT alter status)
```

### The 6 Mandated Scenarios Verified:
1. **Scenario 1 (Mandatory Turnover Failure)**: Company has INR 15M; Tender mandates INR 40M. Engine computes `FAIL`. Reconciliation guard outputs `NOT_ELIGIBLE` and 0% score. AI is blocked from modifying outcome.
2. **Scenario 2 (Missing Proof)**: Valid turnover, but required GST proof is absent. Engine computes `MISSING_EVIDENCE`. Overall status is `PARTIALLY_ELIGIBLE`, providing an actionable upload checklist.
3. **Scenario 3 (Fully Compliant)**: All financial, experience, certification, and mandatory document criteria satisfied. Status is `ELIGIBLE` with 100% score.
4. **Scenario 4 (Ambiguous Clause / Admin Review)**: When conflicting values exist (e.g. 4 Cr in NIT vs 5 Cr in RFP), the extraction service flags `NEEDS_REVIEW`. Rules engine ignores unapproved proposals until reviewed.
5. **Scenario 5 (Ungrounded Citation Rejection)**: When AI proposes a citation referencing an invalid page or non-existent document, the `CitationValidator` rejects it and removes it from the final report.
6. **Scenario 6 (Cross-Company Isolation)**: MSME B cannot access or view compliance evaluations performed by MSME A (`HTTP 404`).
